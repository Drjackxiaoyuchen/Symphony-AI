# Person medical notebooks v1

Method/backup format: `symphony-person-medical-v1`. Reviewed 2026-11-28. UI proposal uses the existing Symphony AI copper/ivory scheme; user visual acceptance remains pending.

## Purpose and estimand

This is a source organization and data-integrity method, not a clinical prediction algorithm. The observable outputs are the exact number of saved source projections and linked observations **within one explicitly selected profile's notebook**, alongside their original values and provenance. Counts are not coverage estimates of a person's medical history. No pooling, imputation, normality classification, risk estimation, patient matching or causal interpretation is performed; statistical uncertainty intervals are therefore not applicable to these deterministic counts.

## Scope and identity review

- The user selects a Family Hub profile and records a nonempty attribution basis before creating a notebook. Nothing is seeded or migrated automatically.
- Each notebook has a distinct localStorage key, `symphony:person-medical:v1:` followed by the JSON-escaped exact profile ID. JSON escaping distinguishes punctuation, Unicode and lone-surrogate IDs without normalization or delimiter collisions. IDs never enter URLs or download filenames.
- The strict envelope contains the format, reviewed identity projection, its canonical UTF-8 SHA-256 fingerprint, review basis/time, update time and source entries. Identity fields are ID, name, birth/death year, life status and identity source/URL; unrelated history, relationships, notes and index-person selection are excluded. The hash is independently checked when reading backups. It detects an inconsistent snapshot; it is neither an authenticity signature nor anonymization.
- An identity-field change holds new source writes and ordinary exports. Explicit same-ID re-review records the new identity and basis while preserving existing source projections. A missing/malformed Family Hub profile cannot authorize writes. Raw recovery remains available for a selected profile ID; deleting a profile does not delete its notebook. After reloading the page, restore the matching Family Hub backup to select an orphaned notebook again; there is no whole-origin notebook inventory.
- Profiles and separate keys are **dataset scopes, not authentication, consent, encryption, access control or verified patient identity**. People using the same browser origin can access its stored data. The user must compare each source Patient with the intended profile; identical names, IDs or hashes do not prove that two patients are the same person.

## Source and restoration gates

FHIR import reuses the [offline single-report projection](medical-records-v1.md) and [namespace-aware reference resolver](fhir-references-v1.md). The notebook preview accepts pasted JSON under 10 MiB, hashes its exact UTF-8 text, retains the offset-bearing clinical timestamp, quantity/comparator, original unit system/code, explicit missing result, source warnings and link-resolution audit, then requires an acknowledgement before append. A pasted-text hash can differ from the original file hash; retain original files separately. This notebook is a structured projection, not a complete source-file vault or a general FHIR processor.

In addition to existing schema and source checks, each notebook permits at most 5,000 unique source IDs, no duplicate source/report/hash tuple, and only one exact nonempty FHIR Patient reference. FHIR entries must retain an absolute Patient fullUrl validated with the offline resolver's URI/type rules and a captured audit containing that Patient subject target. Unqualified `Patient/id` alone and audit-absent legacy projections are held for re-import. Different fullUrls are not aliased, merged or matched across imports. Two notebook owners can have independent Patient sources and the same local source ID; this does not establish whether the source patients are distinct or identical in reality.

JSON backups preserve the reviewed owner and complete source projections. Restoration under 30 MiB is previewed, then explicitly replaces only the selected notebook. A different profile ID, mismatched current identity, altered fingerprint, unsupported format/fields, duplicate ID or inconsistent Patient set blocks replacement. Global source-register ledgers are not person-notebook backups. Restoration never rebinds owner IDs or recalculates source hashes from projected fields. Corrupt notebook bytes are preserved; normal edits/exports are blocked, with a raw backup and validated replacement path.

Actions capture the exact notebook bytes and canonical profile identity. They re-read both before write/export and again after asynchronous validation/hashing. Switching profiles invalidates pending previews/actions; changing pasted text clears its preview. This detects stale-view overwrites. localStorage offers no atomic compare-and-swap or cross-tab transaction: simultaneous independent writers are not serialized. Use one editing tab for a notebook. Browser quota may be reached below the schema limits; write errors are surfaced and original bytes remain in place.

Source removal and one-step undo operate within the selected store. Existing `medical-records`, `record-ownership`, other personal imports and default personal reports remain unchanged. No whole-origin discovery/export or automatic legacy copy is included. Raw backups may contain identifiers and should remain private.

## Local validation and limits

`tests/person-medical.test.ts` uses invented fixtures and an in-memory storage adapter to test key collision cases, independent Node SHA-256 agreement, strict/fingerprint backup validation, two-owner separation with different Patient identities and identical source IDs, preservation of legacy store bytes, wrong-owner/global-ledger backup rejection, within-notebook duplicates/subjects, unqualified/legacy FHIR gates, identity-change renewal, missing/corrupt profiles, stale snapshots, pending-action cancellation, corruption repair and exact source-field round trips. These are deterministic contract/reference cases, not clinical identity accuracy or real-world interoperability measurements.

Desktop/mobile checks and captured synthetic previews are recorded separately in [validation evidence](../validation/person-medical-2026-11-28.json). They cover representative flows in one browser, not all devices, cross-tab concurrency, browser quotas or independent clinical data. No medical or genome records from the user were used in testing.

Next: explicitly reviewed transfer/copy from the legacy register, preserving the original source, attribution compatibility and owner history; then a versioned cross-import namespace/alias policy before accepting multiple source Patient identities in one notebook.
