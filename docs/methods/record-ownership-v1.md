# Medical Records: explicit source attribution v1

Proposal implemented 2026-11-24. Method: `symphony-record-ownership-v1`. Browser inspection is blocked; this change is retained in a pull request pending desktop/mobile verification. User visual acceptance is pending separately.

## Question and outputs

The estimand is a deterministic count/set of saved, explicitly user-attributed records whose declared source and person-identity projections remain unchanged. It is **not** the probability of a correct patient match, true ownership, clinical completeness, disease risk or authorization to access/disclose records. There is no identity model, name-based auto-selection or inherited relationship inference.

Medical Records retains its existing source register. An attribution ledger (`symphony:record-ownership:v1`) records the selected record ID, person ID, display-name snapshots, original subject reference, review basis, review time, method and two SHA-256 fingerprints. Exactly one entry per record ID is allowed, with at most 5,000 entries. Replacement is explicit, reversible by re-review; this is a current-state register, **not an immutable audit history**.

Preview shows source title/provider/date/subject/observation count beside the chosen Family Hub person's identity/source context. Neither person nor record is selected automatically. A nonempty basis, preview and explicit acknowledgement precede save. Existing records and profiles are neither moved nor edited. Missing identity context remains unknown; the reviewer must use the original source, not infer identity from labels.

## Fingerprint contract and validity gates

The full validated MedicalRecord projection is hashed. Any change, including annotations, source file/hash, timestamps, status or observations, holds an existing link for re-review. Person hashing covers exactly `id`, `name`, `birthYear`, `lifeStatus`, `deathYear`, `source`, `sourceUrl`. Changes to these hold the link; changing unrelated history, relationship assertions, notes, index-person flag or review time does not. This is a deliberately bounded identity projection, not a claim that other fields can never affect identity.

Serialization recursively sorts plain-object keys, preserves array order and JSON string escaping, and encodes finite numbers using JavaScript JSON/binary64 semantics. SHA-256 operates on UTF-8 bytes. Non-JSON values are rejected. This is a versioned application projection, not a claim of RFC 8785 compliance. Hashes detect projection changes; they do not authenticate a source, prevent a forged backup or establish biological identity.

The source and family validators run before compatibility review. Duplicate source IDs are rejected. Attribution backups use strict entry schemas, unique IDs, method/hash validation and a workspace constraint: the same exact nonempty source Patient reference cannot target different person IDs, including stale/orphan entries. Empty subjects are not matched. Reference equality is scoped to this workspace; relative identifiers from different servers are not globally unique. The existing Medical Records store still permits only one exact nonempty Patient reference across its FHIR subset records; broader multi-person FHIR imports are not implemented by this attribution layer.

Statuses are `current`, `record missing`, `profile missing`, `record changed`, `profile changed`. Missing objects are checked before hash comparisons; record change takes precedence over person change. A status denotes the first detected hold reason, not an exhaustive diagnosis. Missing/changed links remain saved and are never silently reassigned or refreshed. Explicitly preview again or revoke after reviewing the sources. Source-record and profile restores do not automatically restore attribution; attribution restores do not create missing sources or refresh hashes.

Preview/save/export compare snapshots of all three raw browser ledgers across asynchronous hashing; changed snapshots block the action. Revocation checks the latest stored entry, and undo refuses to overwrite a newly saved attribution. These are best-effort stale-view guards, **not cross-tab transactional locking**. Browser local storage is unencrypted and shared by the origin. Person profiles are data containers, not authenticated users, consent records or access-control boundaries.

## Export boundaries and denominators

- Selected-person medical JSON includes only that profile's identity projection and current reviewed records with their attribution/provenance. Other profiles, family histories and other personal imports are not expanded. Held entries list record IDs/reasons with `completeForSavedAssignments: false`; even `true` means only that saved entries are current, not clinical completeness. An empty export is possible and carries this scope.
- The default personal report contains only source records **without any attribution entry**. Every attributed record is withheld regardless of fingerprint status or whether the profile still exists. Source-record/attribution read errors disable the full download; unreadable attribution also suppresses source records in the rendered/printable report. Family identities and attribution basis are absent; only withholding counts/scope travel with the main report.
- Medical Records' explicitly labeled **all-record** source index and source JSON backup still contain all sources. Attribution index CSV/JSON is a separate all-attribution backup. These are workspace exports, not selected-person exports. Review before sharing. CSV uses the existing formula-escaping serializer.
- `unassigned source records` counts existing source rows with no attribution entry; `current reviewed links` and `held links` count attribution entries, including orphans. Orphan entries do not inflate the source-record denominator. Revoke returns an existing source record to the unattributed default report; the UI discloses this consequence.

No personal source record or genome is uploaded to a third party. No OCR, remote patient matching, model inference, clinical interpretation or paid/gated integration was added.

## Synthetic review setup

In a disposable browser origin only, restore [the existing invented Family Hub profiles](../examples/family-profiles-synthetic.json) through **Family Hub → Import JSON backup**. Then restore [two invented source records](../examples/record-ownership-sources-synthetic.json) through **Medical Records → all-record source backup → Import JSON backup**. Each restore replaces that module's current records. The new attribution backup is a different module: do not put the source backup there.

No attribution is included or auto-created. Choose source A and a person, enter a synthetic review basis, preview, acknowledge and confirm. Source B should remain unassigned. Export the selected person and default report; then edit source A's metadata to exercise the held-link path. This is a manual review recipe, not a browser test claimed completed today.

## Local validation and remaining gate

`tests/record-ownership.test.ts` adds 13 reference cases to the previous 99 (112 total): an independently specified canonical UTF-8 string and Node crypto SHA-256 reference; no automatic assignment; hand-specified two-person/two-record exports; changed/missing record/profile holds; unrelated history edits; exact-subject conflict; malformed/duplicate backups; stale-preview guard; FHIR zero/comparator/absence/unit/source-hash retention; main-report exclusion and CSV escaping; duplicate source IDs; and exact 5,000-link coverage with a cached person digest. Tests validate deterministic data contracts, **not patient-match accuracy**. A local descriptive 5,000-link review took about 151 ms on the first run; this is not a browser/device performance guarantee or identity benchmark.

Final `npm test` (112/112), `npm run typecheck`, `npm run build`, research-doc generation and `git diff --check` passed. No dependency was added. Browser-control attempts timed out repeatedly for the in-app browser and an alternate Chrome selection before any page inspection.
