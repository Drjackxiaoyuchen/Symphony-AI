# FHIR reference identity audit v1

Implemented 2026-11-26. Method: `symphony-fhir-references-v1`. This is the namespace-resolution foundation for the queued person-scoped source stores; that larger migration is not implemented here. The existing copper/ivory UI remains a proposal awaiting user acceptance.

## Estimand and supported contract

For a supported single-report Bundle, the output is the set of literal subject/result links, their referring resource identity, original reference, resolved in-Bundle target and resolution mode. The denominator is one report subject plus one result and one subject per linked Observation: **1 + 2n**, at most 2,001 for 1,000 observations. It is deterministic source bookkeeping, without a patient-match probability, disease inference or claim of authenticated identity. No statistical confidence interval is relevant to this contract; correctness is checked against specified reference cases.

The previous parser indexed a global `resourceType/id` alias for every resource, even when its fullUrl came from a different server. A short ID could therefore resolve outside the referring resource's namespace. The replacement indexes exact fullUrls only. Absolute HTTP(S) and URN references require an exact target in the Bundle. Relative `Type/id` resolves using the RESTful base of the **referring** entry's fullUrl. The inferred target must exist in the Bundle with the expected resource type. Duplicate fullUrls, RESTful fullUrl/type/ID contradictions, conflicting Reference.type and missing Patient/Observation targets block the complete import. No external request or partial save occurs. Literal references take precedence over supplementary identifiers; identifier-only patient matching is unsupported.

Relative references without a RESTful source fullUrl are blocked, including those under absent, opaque or URN source identities. URN Bundles can use explicit fullUrl references throughout. Contained, conditional, version-specific, credentialed, dot-segment, query-bearing and fragment-bearing references are outside this bounded implementation. Exact string identities are retained; URL/case/percent-encoding aliases are not normalized. A legitimate alias may require review rather than automatic acceptance. These gates implement a supported subset, not a full FHIR validator or resolver.

All other existing import gates remain: one report, one Patient identity, supported statuses and flat quantitative/absent observations, explicit units/date precision, duplicate exclusion and no remote lookup. The workspace-wide single nonempty FHIR subject constraint remains. Separate source storage and cross-import identity namespaces are still required before broad multi-patient imports. A newly qualified subject may also differ from an old saved short reference for the same alleged person; the existing workspace gate can reject that mix. No equivalence is guessed and no legacy record is overwritten.

## Provenance and compatibility

New imports save optional `referenceAudit` metadata with the method and all resolved links. The UI exposes original/reference/target/mode in preview and saved source details. CSV appends method and audit JSON columns after existing columns; JSON backups, reports and person exports retain the field. Quantities, comparators, missing values, original units, collection timestamps and source SHA-256 remain unchanged by resolution.

Pasted input is hashed over its exact UTF-8 text and labeled `pasted-fhir.json`; the UI/export warn that this may differ from original file bytes. File input retains its original byte hash. Both paths use a 10 MiB bound and strict UTF-8 decoding. Editing/clearing/discarding invalidates preview and acknowledgement; request tokens prevent an older asynchronous read/hash from returning a superseded preview. Save requires explicit source review and runs the current ledger's validation.

Legacy records are not reparsed or given fabricated audit entries. The optional schema field has no default, so existing validated projections and attribution digests are unchanged. Their UI says when a reference audit was not captured. Re-importing original data to use current checks is an explicit action; edited/new projections require attribution re-review. Backups are user-supplied snapshots, not cryptographic attestations; audit content is not independently re-derived without the original Bundle.

## Primary references, accessed 2026-11-26

- [FHIR R4 4.0.1 Bundle resolution](https://hl7.org/fhir/R4/bundle.html#references) and [Resource References](https://hl7.org/fhir/R4/references.html): relative bases, exact fullUrl matching, resource types and unsupported/ambiguous resolution. [Specification license: CC0](https://hl7.org/fhir/R4/license.html); third-party terminology and trademark rights remain separate. Our stricter offline gates do not claim full conformance.
- [Synthea pinned source](https://github.com/synthetichealth/synthea/tree/0857400eacbbecc5a67c7d05740efa227d22db39): README, Apache-2.0 LICENSE and `src/main/java/org/mitre/synthea/export/FhirR4.java` inspected. Its resource-to-resource fullUrl references informed an exact-URN reference case and the separation of synthetic examples from clinical evidence. No source or corpus copied, generator run or clinical-realism result reproduced.
- [Lindisfarne M1 Hugging Face card](https://huggingface.co/datasets/Toridion/lindisfarne-m1) screened, CC BY 4.0 as declared by publisher. The card describes wholly synthetic records and no real-patient calibration; the hosted viewer reported a schema-casting error. It was not downloaded or integrated, and its realism/performance claims were not reproduced. Our small independently specified fixtures remain the validation data. Relevant bioRxiv/arXiv screening did not supply an adopted model for this deterministic namespace task; the previously reviewed patient-linkage preprint is not a reference-resolution benchmark.
